# 旧系统重构方案论证：模版工程 + 统一组件库（为主）

本文档论证在 **当前存量形态与交付约束** 下，优先采用 **「模版项目 + 统一组件库」**，而不以 **无界微前端** 作为主架构路线的合理性。文末 **§5** 为已定结论；§2 为事实前提，**§4 为具体分析**（用大家能感知的场景讲清为什么这样选），§6 为落地注意点。

---

## 1. 论证目标与结论占位

**结论（详见 §5）**：在「一套仓库承载多产品线、打包后仍按域名拆分部署、各产品线独立 UI 与登录、无法在集团层强制统一壳布局」的前提下，引入无界微前端 **增益有限**，反而增加 **宿主与子应用的嵌套层级与治理成本**；更合适的路径是 **模版工程规范化 + 组件库统一公共业务组件与登录等逻辑层，UI 由各域项目自持**。

下文所有对比均围绕上述约束展开，而非抽象比较两种技术孰优孰劣。

---

## 2. 事实前提（来自 `当前管理后台前端项目` 与我们当前交付方式）

### 2.1 代码形态

- **单体仓库内多套「逻辑上的项目」**：路由按业务域拆分（如 `/order`、`/thepool`、`/isacommunity`、`/academy`、`/ems`），共享同一套基建（Vue2、Vuex、Axios、权限守卫、多套登录页等）。
- **动态菜单 + 动态路由**：后端菜单驱动 `formatRoutes`、`addRoutes`（见 `router/avue-router.js`），与单体目录深度耦合。
- **多租户**：`tenantId` 切换不同顶栏、侧栏、Logo、首页（见 `page/index`、`const/website.js`、`const/redirect`）。

### 2.2 交付与访问形态（论证核心约束）

| 约束 | 含义 |
|------|------|
| **打包与部署仍按产品线拆到不同域名** | 用户认知与运维边界是「不同站点」，不是「同一 URL 下一页切换子应用」。 |
| **各项目 UI 无法集团统一** | 品牌、布局、登录视觉随租户/产品线变化，无法在壳层做成一套固定布局强加给所有域。 |
| **只能统一逻辑层** | token、刷新、权限、axios、登录流程编排、公共业务组件行为等可收敛；外观不能一刀切。 |

在此前提下：**微前端最核心的体验诉求——「单一门户 URL 内嵌多应用」——与现状目标不一致**，这是论证的枢纽。

---

## 3. 两种模式在本议题中的定义（简述）

### 3.1 模式 A：无界（微前端）

主应用（壳）嵌入多个子应用运行时；典型价值是 **运行时集成、同源或强网关下的拼装、独立发版与子应用隔离**。

与本仓库：`main-app` / `sub-app` 仅作技术演示，**不代表**结论必须采用该形态。

### 3.2 模式 B：模版工程 + 统一组件库

每个产品线独立前端工程（可多仓或 monorepo 分包），共用 **脚手架模版**；**组件库（含 auth-sdk）**承载公共业务组件与 **登录/权限等逻辑**；**各应用自行实现登录页与布局 UI**。

---

## 4. 具体分析：结合现状，为什么优先模版 + 组件库，而不是先把无界当主干

按 **用户怎么访问、我们怎么部署、无界多干了什么、能不能解决我们的真问题** 来讲。

---

### 4.1 先弄清：无界这类微前端，最擅长解决哪类「疼」？

可以把它理解成：**在一个「总门户」页面里，把别的系统一块块嵌进来**，让人觉得自己一直在同一个网站里切换模块。

它很适合这类目标：

- 公司希望对外只有一个入口地址（例如 `portal.xxx.com`），里面左边菜单点来点去，其实是好几个团队维护的前端；
- 或者强依赖「同一浏览器页里嵌多个子系统」，又要隔离样式和脚本。

也就是说：**它的强项是「合成一个门户体验」**，而不是天然等于「拆仓库、拆部署」——拆仓库用 monorepo、多包、多 CI 也能做，不一定要上无界。

---

### 4.2 我们的实际情况：用户本来就是「去不同站点」，不是「先进总门户」

当前约束里已经写明了：

- 打包上线后，**各产品线还是各自域名**（例如不同业务走不同域名，用户书签、对外宣传链接也是按站点记的）；
- **每个站的界面、登录页长得不一样**，集团层面也**没法**强行规定「大家都用同一套顶栏侧栏皮肤」。

在这种模式下，用户日常心智是：

> 我去 A 系统就上 A 的域名；去 B 系统就上 B 的域名。

这时如果为了「微前端」再做一个 **壳站点**，常见画面会变成：

- 用户先到 `portal.xxx.com`，壳里再用无界去嵌 `pool.xxx.com`、`manager.xxx.com`……
  ——等于 **多绕一层**，而且跨域嵌页面时，登录态、Cookie、第三方登录回调，仍然要按 **统一登录（SSO）** 那一套来设计，**无界本身并不替你解决「多个域名怎么共用一个账号体系」**。

反过来说：
若最终用户 **根本不经过门户**，还是 **直达各域名**，那壳 + 无界往往就变成 **运维和研发多维护一套「宿主」**，业务侧感知不强，成本却实实在在（壳要发版、嵌入要配置、出问题要多疑一层「是壳还是子应用」）。

**一句话**：我们现在的交付形态，和「无界最擅长的那种单一门户 URL」**本来就不对齐**；在这前提下先上大壳，容易变成 **加了一层技术夹心**，而不是解决当前最痛的拆分与复用问题。

---

### 4.3 「UI 不能统一」时，壳很难当「全家通用外壳」

很多微前端文章里的示意图，都是：**壳负责顶栏、侧栏、菜单，子应用只管中间内容区**。

我们已经判断：**做不到**——不同产品线登录页、主题、布局都要自己把控。

那就面临一个很具体的问题：

- **若壳不能做统一导航和皮肤**，壳还剩什么？往往只剩一个 **「透明容器」**：里面嵌子应用，外面看起来壳自己没什么统一视觉收益。
- 这时和「各域名独立打开一个完整 SPA」相比，**用户侧差异不大**，开发侧却要多维护：**壳工程、主子通信、加载失败谁兜底、版本谁对齐**。

所以：**不是无界技术不行，而是「我们不需要那个统一壳带来的体验」，却要承担壳的复杂度**，性价比容易偏低。

---

### 4.4 登录和跨域：要优先搞清的是「账号体系」，不是「嵌页面」

现实里多个域名要「感觉像一家公司的系统」，业界普遍做法是：

- **统一身份（SSO / 统一认证中心）**：用户在中心登录一次，各站点通过票据或 token 认出是同一个人；
- 各站点自己的前端负责：**把 token 存好、请求带上、过期刷新、退出清干净**——这些正是 **组件库 / auth-sdk 擅长封装** 的「逻辑层」。

无界嵌跨站页面时，**Cookie、存储、第三方 OAuth 回调域名** 仍然要按浏览器规则来，该上的 SSO 还是得上。**嵌套框架替代不了统一登录设计**。

所以在「多域名 + 各站自建 UI」的路线下，更顺手的顺序通常是：

1. 先把 **登录与安全逻辑** 抽成库，各站调用同一套；
2. 和后端一起定 **SSO / 换票** 怎么玩；
3. 若将来产品强制「必须一个门户 URL」，再考虑 **门户 + 嵌入**（那时再上无界也有明确业务抓手）。

---

### 4.5 从旧单体往外拆：我们立刻要动刀的是「菜单、路由、接口」，不是先立壳

旧工程里菜单和路由是绑在一起的（后端返回菜单再 `addRoutes`），拆成多个站点之后，**不管用不用微前端**，都要重做：

- 每个站点自己的菜单从哪来、和权限怎么对应；
- 路由怎么不再写死在同一个大目录里。

若 **没有统一壳 UI**，却先立一个 **壳工程**，还会多出一件事：**壳上的菜单怎么和每个子站里的路由对齐**（路径、权限、埋点），沟通成本和联调成本都会上去。

反过来：**模版 + 组件库** 的路线是：

- 每个产品线一个工程，菜单就在 **自己工程里** 长出来，和部署域名一一对应，和当下「各站独立」的现状 **最好接**；
- 组件库只管 **大家都要用的按钮逻辑、表格行为、登录鉴权**，不强迫 UI 长一样。

---

### 4.6 小结：模式 B 为什么更贴我们现在的「能做什么、不能做什么」

| 我们能统一的 | 更适合放在哪 |
|--------------|----------------|
| 登录鉴权、token、刷新、axios、权限清理、公共业务组件行为 | **组件库 / auth-sdk**（模式 B 的核心） |
| 各站长得不一样的登录页、皮肤、布局 | **各产品线工程自己画**，库只提供 hooks / 协议，不强行套壳 |

| 模式 A（先上大壳 + 无界）在当前约束下的尴尬点 | 通俗说法 |
|-----------------------------------------------|----------|
| 用户仍直达各域名 | 壳常常用不上，却要多维护一套 |
| UI 不能统一 | 壳没法当「全家通用外壳」，容易退化成薄容器 |
| 多域名会话 | 仍要走 SSO，无界不是捷径 |
| 拆单体 | 菜单路由本来就要重做，不会只因上了无界就变简单 |

---

### 4.7 一句话对照（仅在「多域名 + 非统一 UI」前提下）

- **模版 + 组件库**：先把你 **已经决定要强制的「逻辑层」** 做实，和各域名独立部署 **顺手对齐**。
- **无界做主架构**：更适合 **明确要「一个门户 URL 里聚合多应用」** 时再重点投入；在当前结论里，它更适合将来 **增量评估**，而不是本轮主干。

---

## 5. 结论（项目组采用方案）

当前系统本质是 **一套代码仓库内承载多条产品线**，打包发布后 **仍按产品线部署在不同域名**；每条线 **有不同的 UI 与登录形态**，客观上 **无法在集团层面统一布局和 UI**，能够做到的是 **统一逻辑层**（鉴权、请求、权限、公共业务组件行为等）。

在这种情况下，引入 **微前端框架（如无界）作为主干** 的收益有限：**无法消除「各站独立入口」的现实**，却会 **在当前架构上再增加一层微前端宿主与子应用的嵌套关系**，带来额外的集成、发布与排障成本，却不能解决「UI 不统一」这一根本约束。

因此 **不将无界微前端作为本轮重构的主架构**，而采用：

- **模版项目**：统一工程脚手架、目录、构建与 CI 规范，降低多工程并行成本；
- **统一组件库**：承载 **公共业务组件** 与 **统一登录及相关安全逻辑**（如 token、刷新、拦截器、登出清理等）；
- **各产品线项目自行控制 UI**（含登录页与各域布局），在逻辑层与组件行为上与组件库对齐。

若未来出现 **强制单一门户域名、必须在同一 URL 内聚合多产品线** 的产品诉求，再 **单独评估** 是否引入壳 + 微前端（或统一门户 + SSO 跳转策略），作为 **增量能力** 叠加，而非否定当前以模版 + 组件库为主的路径。

---

## 6. 落地要点（支撑结论的执行层）

1. **优先沉淀 `auth-sdk`（或组件库内的认证模块）**：与后端 OIDC/SSO 路线对齐，避免各站重复实现换票与刷新。
2. **组件库边界**：明确「只收逻辑与可复用业务组件」，不把各域独有页面塞进库中，防止库膨胀。
3. **设计规范**：无法统一 UI 时，仍建议 **设计令牌 + 登录页必需字段/无障碍清单**，减少体验漂移。
4. **文档与评审**：将「多域名 + 非统一 UI」写入架构基线，避免后续方案评审仍默认「要有统一壳」。
